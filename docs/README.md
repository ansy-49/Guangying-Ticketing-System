# 光影票务工程文档

> 文档基线：当前工作区代码，更新于 2026-10-06。

本目录用于系统化说明“光影票务——电影购票系统”的业务模型、架构决策、核心链路、一致性方案与工程边界。文档以仓库中的实际实现为准，不把规划中的能力描述为已经上线的功能。

## 1. 阅读约定

文档中的能力按以下口径描述：

- **已实现**：当前代码中存在完整入口、业务逻辑与数据落点。
- **降级实现**：本地演示模式可运行，但会绕过或替代外部中间件。
- **演进项**：合理的生产化方向，当前代码尚未完整实现。

需要特别注意：本项目当前是一个 **多模块单体**，不是微服务系统。RocketMQ 的生产者与消费者、定时任务以及 HTTP 接口均由同一个 Spring Boot 应用承载；模块拆分用于约束代码职责，不等于独立部署。

## 4. 文档真实性边界

以下事实是理解项目时最重要的边界：

- MySQL 是用户、排片、订单、库存、座位成交结果和 Outbox 事件的权威数据源。
- Redis 中的缓存、排队信息、入场令牌、临时座位锁和已售投影均可过期或重建，不能单独作为最终交易凭证。
- Waiting Room 只对管理员显式标记的热门场次生效，普通场次直接放行。
- 订单超时以 RocketMQ 5 定时消息为主触发器，并由支付懒过期和 MySQL 分批扫描兜底；所有入口共享同一条 CAS 关单链路。
- 支付是站内积分扣减，不包含第三方支付、退款对账与资金清结算。
- 本地默认模式使用 H2 和降级配置；Docker 完整模式才会同时接入 MySQL、Redis 与 RocketMQ。
- 压测结果是同环境、单实例、固定数据集下的 A/B 对比，用于证明优化方向，不等价于生产容量承诺。

## 6. 文档维护规则

- 修改交易链路时，同时更新业务流程、状态机和一致性边界。
- 新增中间件能力时，必须写清生产者、消费者、数据权威方和失败补偿方。
- 性能数字必须保留测试环境、请求规模、并发度和对比基线。
- 设计模式只描述真实变化点，不把普通 `if/else` 包装成模式。
- 规划能力必须明确标注为“演进项”，不能与已实现能力混写。
