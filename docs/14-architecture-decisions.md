# 14. 架构决策记录（ADR）

本文件记录关键选择、替代方案和适用边界。目标不是证明当前方案永远正确，而是让后来者知道“当时解决什么问题、付出什么代价、何时需要重选”。

## ADR-001：采用多模块单体

**状态**：已采用。

**问题**：项目需要清晰边界，但业务规模和团队规模不足以支撑微服务运维成本。

**决策**：使用 domain、common、dao、service、biz、provider Maven 模块，最终打包为一个 Spring Boot 应用。

**收益**：保留本地事务、部署简单、调试方便，同时能表达依赖方向。

**代价**：模块不能独立扩缩容；provider 当前可通过传递依赖直接访问 service，边界不是强制隔离。

**重新评估条件**：某业务域需要独立扩缩容、独立发布团队和独立数据所有权。

## ADR-002：MySQL 作为交易权威，Redis 只做临时状态和投影

**状态**：已采用。

**问题**：Redis 速度快，但会过期、淘汰、故障或丢失，不能独立承担订单与库存账本。

**决策**：订单、积分、库存和成交座位以 MySQL 为准；Redis 承担缓存、排队、入场租约、临时座位锁和已售投影。

**收益**：交易可审计、可事务化，Redis 丢失后能够重建。

**代价**：需要事务回调、补偿和对账处理跨资源短暂不一致。

**被否决方案**：仅用 Redis 扣库存并异步写库，故障恢复与审计成本过高。

## ADR-003：Caffeine + Redis 两级 Cache Aside

**状态**：已采用。

**问题**：热点查询既要低延迟，又要跨实例共享。

**决策**：Caffeine 承担短 TTL 本地热点，Redis 承担较长 TTL 共享缓存；未命中通过 Loader 回源数据库。

**收益**：减少 Redis 网络访问和数据库查询；Redis 故障时可降级。

**代价**：L1 多副本存在短暂不一致，需要 Pub/Sub 失效和 TTL 收敛。

**重新评估条件**：数据更新极频繁或要求读后立即一致时，减少/取消 L1，改用版本化读取或直接数据库。

## ADR-004：single-flight + Redisson 治理热点回源

**状态**：已采用。

**问题**：热点 key 过期时，同实例和多实例可能同时回源。

**决策**：本地条带锁合并单实例请求，Redisson Key 锁协调跨实例，持锁后再次检查缓存。

**收益**：正常情况下一个 key 只有一个 Loader 执行。

**代价**：依赖 Redis；锁等待超时后为可用性仍可能重复回源；条带哈希冲突会带来无关等待。

## ADR-005：接口限流与 Waiting Room 分层

**状态**：已采用。

**问题**：用户级防刷无法控制一个热门场次的总体洪峰。

**决策**：滑动窗口/令牌桶控制单调用方速率，Waiting Room 控制场次级同时准入人数。

**收益**：把流量治理前置，保护 Redis Lua 和数据库事务。

**代价**：用户需要等待；必须维护 token、lease 和回收任务；参数需要压测调优。

**被否决方案**：所有用户直接抢数据库锁，虽然可防超卖，但连接池和锁等待会成为瓶颈。

## ADR-006：Lua 前置锁座 + MySQL 条件更新和唯一索引

**状态**：已采用。

**问题**：场次级乐观锁让购买不同座位的请求产生无关版本冲突。

**决策**：Lua 原子批量预占具体座位，MySQL 用条件更新扣总库存，座位唯一索引做最终裁决。

**收益**：不同座位并发不再争用同一版本号，同时保持零超卖底线。

**代价**：Redis 和 MySQL 之间需要回滚补偿；系统包含总库存和具体座位两种一致性维度。

**被否决方案**：只用唯一索引会让大量冲突晚到数据库才失败；只用 Redis 无法提供最终账本。

## ADR-007：建单同步完成，领域副作用异步化

**状态**：已采用。

**问题**：用户需要立即获得订单号，但缓存投影、通知等副作用不应拉长关键事务。

**决策**：锁座、库存和建单在一个同步请求中完成；订单领域事件通过 Outbox + RocketMQ 异步处理。

**收益**：用户能确定建单结果，非关键副作用解耦。

**代价**：投影短暂滞后，需要最终一致性和观测。

## ADR-008：Transactional Outbox，而不是提交后直接发 MQ

**状态**：已采用。

**问题**：数据库提交和 MQ 发送无法用普通本地事务原子完成。

**决策**：业务数据与 Outbox 同事务落库，调度器通过条件抢占、发送租约和重试投递。

**收益**：Broker 暂时不可用或应用崩溃时事件仍可恢复。

**代价**：至少一次语义带来重复消息；Outbox 表、扫描器、DEAD 运维增加复杂度。

**被否决方案**：提交后 best-effort 直接发送存在不可恢复丢消息窗口；XA 对当前规模过重。

## ADR-009：消费端数据库唯一键幂等

**状态**：已采用。

**问题**：发送成功但标记 SENT 前崩溃会重复投递。

**决策**：消费者先插入 `processed_event(event_id)`，与数据库副作用同事务；唯一键冲突直接跳过。

**收益**：重复消息不会重复执行数据库副作用。

**代价**：幂等表需要保留和清理；Redis/外部 API 副作用仍需单独幂等或可重建。

## ADR-010：定时消息主触发、数据库扫描兜底

**状态**：已采用。

**问题**：订单 15 分钟未支付需要释放库存和座位。

**决策**：建单事务同时写 `ORDER_TIMEOUT_CHECK` Outbox，提交后由 RocketMQ 5 专用 DELAY Topic 按绝对截止时间投递。消费者、支付懒过期和每 60 秒数据库扫描都调用同一个 `OrderCloseService`；数据库以 `status=PENDING` 条件更新裁决，扫描按组合索引分批执行且每单独立事务。

**收益**：正常情况下接近截止时间关单；Outbox 避免建单成功却未登记超时任务；重复消息、支付竞争和多实例扫描不会重复返库存；Broker 故障或漏消息仍能最终收敛。

**代价**：需要显式初始化 DELAY Topic并维护消息、Outbox 与扫描三套监控；扫描仍存在周期性数据库成本。

**边界**：Broker 接收定时消息不等于消费者一定成功，故不能删除支付懒过期与扫描兜底。

## ADR-011：JWT 无状态认证与数据库管理员复核

**状态**：已采用。

**问题**：普通 API 需要轻量认证，管理操作需要及时反映角色变化。

**决策**：JWT 提供用户身份；管理员权限不只信任客户端或旧 Token，而是由 Service 查询数据库角色。

**收益**：普通请求无需服务端 Session，管理员撤权较及时。

**代价**：Token 72 小时内难以撤销；管理请求多一次数据库查询。

## ADR-012：H2 本地模式与 Docker 完整模式并存

**状态**：已采用。

**问题**：完整中间件启动成本高，但项目需要开箱即用。

**决策**：默认 H2 并排除 Redis/Redisson，Docker profile 启用 MySQL、Redis、RocketMQ。

**收益**：开发和演示门槛低，完整模式仍能验证中间件链路。

**代价**：H2 可能掩盖 MySQL 并发和 SQL 方言问题；降级模式不能作为分布式能力证据。
